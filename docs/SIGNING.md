# Mikozora Android signing

Mikozora's GitHub Releases must be signed with one permanent, project-owned
keystore. Android treats the signing certificate as part of the app identity:
an APK can update an installed copy only when the application ID and signing
certificate match and the new `versionCode` is higher.

> **Do not send the keystore or its passwords in chat, email, an issue, or a
> pull request. Do not commit them to Git.** The repository ignores common
> keystore extensions as a second line of defence.

Existing v0.10.0–v0.12.0 GitHub APKs were debug-signed and do not become
permanently signed retroactively. The first permanently signed build must use
a new version. Moving from a debug-signed installation to that build requires
one uninstall/reinstall; after that, permanently signed releases can update in
place.

## 1. Create the keystore on your own computer

Keep the original outside this repository—for example, in an
`AndroidSigning` folder in your user profile.

You need `keytool` from JDK 17 or Android Studio's bundled JDK. Typical
locations are:

- Windows: `C:\Program Files\Android\Android Studio\jbr\bin\keytool.exe`
- macOS: `/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/keytool`
- Linux: `keytool` from an installed JDK

Run:

```sh
keytool -genkeypair -v -keystore /path/outside/the/repo/Mikozora-release.p12 -storetype PKCS12 -alias Mikozora -keyalg RSA -keysize 4096 -validity 10000
```

Use a strong, unique password generated by a password manager. `keytool` will
ask for the keystore password, identifying information, and a password for the
key itself. The alias must be exactly `Mikozora` if you use the value in the
secret table below.

Verify the new key without sharing its password:

```sh
keytool -list -v -keystore /path/outside/the/repo/Mikozora-release.p12 -storetype PKCS12 -alias Mikozora
```

Record the certificate SHA-256 fingerprint with the backup. The fingerprint
is public information; the keystore and passwords are not.

### Back it up before continuing

Keep at least two protected copies of the `.p12` file in separate locations
and store both passwords and the alias in a password manager. Test that a
backup opens with the verification command above.

If the only copy or password is lost, there is no recovery process that can
make Android accept a newly generated key as an update to installations signed
with the lost key.

Do not use `~/.android/debug.keystore` as the permanent release identity.

## 2. Add the GitHub Actions secrets

In the GitHub repository, open **Settings → Secrets and variables → Actions →
New repository secret** and create exactly these four secrets:

| Secret | Value |
| --- | --- |
| `MIKOZORA_KEYSTORE_BASE64` | Base64 representation of `Mikozora-release.p12` |
| `MIKOZORA_KEYSTORE_PASSWORD` | Password for the keystore file |
| `MIKOZORA_KEY_ALIAS` | `Mikozora` |
| `MIKOZORA_KEY_PASSWORD` | Password for the `Mikozora` key |

Create the Base64 value locally and paste it only into GitHub's secret form:

**Windows PowerShell**

```powershell
$keystore = "$HOME\AndroidSigning\Mikozora-release.p12"
[Convert]::ToBase64String([IO.File]::ReadAllBytes($keystore)) | Set-Clipboard
```

**macOS**

```sh
base64 -i "$HOME/AndroidSigning/Mikozora-release.p12" | tr -d '\n' | pbcopy
```

**Linux**

```sh
base64 -w 0 "$HOME/AndroidSigning/Mikozora-release.p12"
```

Clear the clipboard/terminal afterwards if your system keeps clipboard or
terminal history. GitHub will not display secret values again after they are
saved.

If an existing keystore is JKS instead of PKCS12, convert a copy first; the
workflow intentionally expects PKCS12:

```sh
keytool -importkeystore -srckeystore /path/to/existing.jks -srcstoretype JKS -destkeystore /path/outside/the/repo/Mikozora-release.p12 -deststoretype PKCS12
```

## 3. How CI uses the key

For pull requests and ordinary branch builds, the workflow does not use the
real secrets. It creates a throwaway PKCS12 key solely to verify that
`assembleRelease` and APK signature verification work, then uploads the usual
debug APK as the `Mikozora-Android` artifact.

For a run that will publish a GitHub Release, the workflow:

1. requires all four secrets and stops if any is missing;
2. decodes the keystore into the runner's temporary directory with mode `600`;
3. runs `assembleRelease` with the signing values in environment variables;
4. verifies the APK with `apksigner` and prints its public certificate details;
5. uploads that signed APK for the release job; and
6. removes the temporary keystore.

## 4. Build a signed release locally

Set the same values in your local shell. For example, on macOS/Linux:

```sh
export MIKOZORA_KEYSTORE_PATH="$HOME/AndroidSigning/Mikozora-release.p12"
export MIKOZORA_KEYSTORE_PASSWORD='…'
export MIKOZORA_KEY_ALIAS='Mikozora'
export MIKOZORA_KEY_PASSWORD='…'
export MIKOZORA_KEYSTORE_TYPE='PKCS12'
cd android
./gradlew assembleRelease
```

The signed APK is written to
`android/app/build/outputs/apk/release/app-release.apk`.

On Windows PowerShell, use `$env:NAME = '…'` assignments and
`.\gradlew.bat assembleRelease` instead. Avoid putting real passwords in a
script that could be committed.

## 5. Verify a downloaded APK

With Android SDK Build-Tools installed:

```sh
apksigner verify --verbose --print-certs Mikozora-vX.Y.Z-Android.apk
```

The SHA-256 certificate digest must match the fingerprint recorded from
`keytool -list -v`. Every future official release should keep that same
fingerprint.
